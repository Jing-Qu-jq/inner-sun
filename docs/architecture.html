InnerSun

System Architecture

An AI psychological-counseling assistant for international students. Our moat is a proprietary knowledge base of researcher-authored personas; the AI retrieves and applies that expertise in real time. The AI is the hook — the goal is to build enough trust that students book a session with a real human counselor.

In plain language
The student's browser only ever talks to our backend — never directly to OpenAI. Our backend (the "orchestrator") is the brain: it figures out what the student needs, looks up the right researcher-authored guidance, asks OpenAI to write a warm reply in that style, checks it for safety, and decides whether it's the right moment to suggest a human counselor. Everything the AI "knows" lives in our database, which our researchers control.
Engineering detail
The orchestrator is a thin, stateless service (Node or Python). Keeping OpenAI calls behind it does three things at once: (1) security — the API key never reaches the browser (today's prototype leaks it, which we must fix); (2) cost control — we cache, tier models, and cap tokens centrally; (3) portability — the provider sits behind one interface, so "we use OpenAI" is a config choice, not a lock-in.

In plain language
Anyone can start instantly and anonymously — that's the "tree hole" promise and the top of the funnel. Logged-in users get their history remembered. For each message, we quietly figure out which researcher cases best fit this student, apply that guidance, write a caring reply, double-check it's safe, and — only when trust is there — gently mention that a real counselor is available.
Engineering detail
Persona matching is a running assessment, re-evaluated as the conversation reveals more — not a one-time gate on the first message. The "relevance floor" is the safety valve: if nothing matches well, we don't force irrelevant clinical strategies; we fall back to general empathetic listening and flag the conversation as a content gap (feeding the flywheel).

Where personas live: Postgres with the pgvector extension. One managed database (Supabase / Neon / AWS RDS) holds everything — persona text, vector embeddings, user accounts, memory, and bookings — with real transactions and one set of backups. We do not need a separate specialty vector database (Pinecone/Qdrant/Weaviate) at our scale; pgvector handles tens of thousands of personas comfortably, and we can graduate later if retrieval volume ever demands it.

Engineering detail
A persona's embedding is computed once, when a researcher saves it, and stored alongside the row — never recomputed at chat time. Adding persona #200 is a pure content task; no code or schema change. Retrieval is ORDER BY embedding <=> :query_vector LIMIT N.

4Caching & Cost Control

Three independent cache layers, each answering a specific cost question.

#CacheWhat it savesNotes / caution
①Semantic cacheThe whole model call for repeated/similar questions Only for non-personal FAQ/info — "Is this confidential?", "How do I book?". Never cache a personalized emotional reply: returning one distressed student's response to another is clinically wrong and unsettling. Match by embedding similarity above a high threshold.
②Persona cacheThe database round-trip for popular personas Personas change rarely, so cache aggressively in Redis with a long TTL; invalidate on edit when a researcher updates one. Their embeddings are already stored (never re-embedded).
③Prompt cachingA large discount on input tokens OpenAI bills the unchanged system-prompt prefix at a reduced rate when reused. Keep static guidance at the front of the prompt so it stays cacheable.

Other ways we save money

  • Model tiering — the biggest lever. Use gpt-4o-mini for cheap, high-volume jobs (classifying the user, summarizing history, safety screening) and reserve gpt-4o for the one thing quality depends on: the counseling reply.
  • History summarization — don't resend the full transcript each turn; summarize older messages so the prompt stays short (tokens = money).
  • Token caps — bounded max_tokens on replies.
  • Cheap, small embedding model (text-embedding-3-small) + an embedding cache.
  • Rate limiting / abuse protection so free anonymous usage can't be farmed for cost.

5Free vs. Paid — Monetization

Recommendation: freemium, but keep the "tree hole" venting free. The free AI chat is the brand promise and the top of the funnel — a paywall on "talk to someone when you're struggling" would poison both trust and acquisition. Monetize the things around it instead.

TierPriceWhat they get
AnonymousFREEInstant AI chat, no memory, rate-limited. The hook.
RegisteredFREEMemory across sessions, saved insights, daily message allowance.
SubscriptionPAID (optional)Unlimited AI chat, richer memory/insights, priority + discounted human sessions.
Human sessionsPAID per sessionBooking a real counselor — the core revenue.
Investor framing
AI chat is deliberately low-margin lead generation — which is exactly why the caching and model-tiering above matter: they push cost per conversation toward near-zero, keeping customer-acquisition cost low. Real revenue is the human session bookings (high value, recurring) plus optional subscription. The data flywheel compounds the moat: more conversations → better personas → better AI → more trust → more bookings.

6Why This Is Defensible

  • Proprietary clinical knowledge base. Competitors are thin prompt-wrappers around the same public models. Our researcher-authored, case-grounded personas are content no model has and no competitor can copy.
  • Editable & traceable. Because expertise lives in a database (RAG), not baked into model weights (fine-tuning), a researcher can correct guidance in one row and it's live instantly — and every reply is traceable to vetted source material. Critical for clinical responsibility.
  • A compounding data flywheel. Real (consented, de-identified) conversations reveal which cases to author next, so the library grows toward actual demand.

7Hard Constraints

Must-haves, not nice-to-haves.

  • Privacy & consent. This is sensitive mental-health data, much of it from Chinese nationals. Anonymous logging requires a clear consent notice; using conversations to author personas requires separate, explicit consent and de-identification before any human review. China's PIPL (esp. cross-border transfer), GDPR for EU students, and special-category-data rules all apply — legal sign-off is required before the flywheel runs. Design consent + logging from day one.
  • Safety. Crisis/self-harm detection with real escalation paths and crisis resources is not optional for a mental-health product.
  • Not a medical device. The AI offers support and coping strategies, never diagnosis — and routes to humans for anything beyond its scope.
